# lime: 要件と方向性

生成した英文の読解を通じて語彙を SRS で習得するツール。
最初期段階の要件整理であり、技術的仕様ではない。

## コアループ

1. その日の due 語と new words から 1 サイクルあたり約 15 語を選び、約 500 語の英文(事実ベースまたは物語)を生成する。文体は SAT、Duolingo English Test、共通テストを想定する
2. スマホまたは PC で読む。文章中の単語はすべてダブルクリックすると辞書ポップアップ(意味と例文、評価ボタン)が開く
3. サイクル完了時、辞書を開かなかったターゲット語は暗黙的に `good` として FSRS に記録する
4. 文章の後に、ターゲット語に強く関連した内容理解クイズ(選択式 5 問)を解く
5. 読解中にダブルクリックして調べた、まだ SRS に登録されていない単語を、読了後にまとめて選んで SRS に追加する(batch add)

## 学習量の目標

- 1 サイクル 3〜5 分、1 日あたり new + review で約 100 語(約 7 サイクル、約 30 分)を目標とする
- 15 語 / 500 語はターゲット語率 3% にあたる。読解研究では 95〜98% の lexical coverage が推奨されるため、これはほぼ上限であり増やす余地はない
- 文脈内での復習は孤立カードより記憶効率が高い可能性があり、その場合は必要 review 数が減る。FSRS のパラメータ最適化に任せて様子を見る

## 語彙レベルの制御

非ターゲット語を既知語に抑える厳密な制御(頻度リスト検証や既知語モデル)は行わない。
プロンプトでおおまかなレベルを指定するだけに留める。
80〜85% 程度の coverage を許容する。
目的は「理解」ではなく「語彙獲得」であり、推定できなかった語は辞書確認から batch add で拾えるため、未知語の混入はむしろ獲得機会になる。
読むのが遅くなりすぎた場合に締める方向で後から調整する。

## 単語選定とテーマ決定

embedding とクラスタリングによるテーマ選定は将来課題とし、当面は LLM に計画させる。
1 日の流れは次の 3 段階。

### Step 1: プール確定

- due 語(例: 70 語)と new words 枠(設定値、初期値 30/day)を FSRS と設定から機械的に決める
- new 候補は当日枠の 2〜3 倍をプールから抽出する。抽出順は基本 import 順

### Step 2: プランナー呼び出し

安いモデルへの 1 回の呼び出しで、全語を 6〜7 グループに分けさせる。
出力は各グループの theme、style(factual / narrative / essay のローテーション)、words の JSON。

- due 語は必ずどこかのグループに入れる
- new 語はテーマに合うものだけ採用し、合わなかった候補は翌日に回す
- 機能語や抽象語はどのテーマにも入るため、プランナーが余り枠として分配する
- 直近 N 日のテーマ履歴を渡して重複を避けさせる。ユーザーの興味分野リストを設定に持たせてもよい

new 語の飢餓対策として、プール滞留日数が閾値(例: 7 日)を超えた語は「必ず入れろ」側に昇格させる。

### Step 3: サイクル生成

グループ 1 つとテーマ、スタイル指定で 500 語をストリーミング生成する。
同じ呼び出しでクイズ 5 問も生成し、各問に関連ターゲット語をタグ付けさせる。
サイクル N を読んでいる間にサイクル N+1 を裏で先読み生成する。

生成後、全ターゲット語の出現チェックを行う。
語義や品詞の一致チェック(polysemy 対策)は未決。

## FSRS へのフィードバック

- **辞書確認**：単語をダブルクリックして辞書ポップアップを開き、ポップアップ内の評価ボタン(again / hard / good / easy)で明示評価する
- **辞書を開かなかった語**：サイクル完了(クイズ画面到達)時に一括で `good` とする。途中離脱したサイクルは未評価のまま due 据え置き
- **クイズ**：非対称に効かせる。誤答時のみ関連ターゲット語を `good` から `hard` に降格し、正答では昇格させない。誤答は「その語の周辺が読めていなかった」シグナルとしてそこそこ信頼できる一方、正答は文脈推測だけでも取れてしまうため
- クイズの正誤ログは全て残し、後続のレビュー成績との相関を見てから重みを再設計する

スクロール通過や表示時間による読了判定は行わない。
読み飛ばした箇所を後から遡って理解する読み方を許すためである。

new 語が辞書を開かないままサイクルを終えた場合は、終了画面で「既知かどうか」を確認する。
new 語は定義上未知のはずであり、review 語とは意味が違うため。

## 読解 UI

- 文章中のすべての単語を辞書確認の対象にする。単語のダブルクリックで、文章の上に辞書ポップアップを表示する
- new 語と review 語には、通常語と区別できる控えめなインラインマークを付ける。マークは辞書を開くための条件ではない
- 評価ボタンは読書面に常時置かない。評価は辞書ポップアップ内で行う
- 辞書ポップアップには意味、1つ以上の例文、SRS未登録語の場合の「SRSに追加」を表示する
- UIはスマホとPCの両方に対応し、テーマはダークモードのみとする

## クイズ

- 選択式 5 問
- 単語そのものではなく、ターゲット語に強く関連した文章中の情報の理解を問う
- 文章と同一の生成呼び出しで作る(grounding のため)

## 辞書

- ユーザーが自分で購入した英辞郎(BOOTH 版テキスト)を手元で import し、クライアントでパースして OPFS 上の SQLite に格納する
- プロダクト側は英辞郎データを配布しないため、複数ユーザーでもライセンス上クリーン
- 英辞郎を持たないユーザー向けに Wiktionary(kaikki.org の wiktextract dump)の import 経路も用意する
- ポップアップの表示内容は意味と 1 つ以上の例文

## 単語の import

- CSV と apkg を import できるようにする
- Sottaku からのエクスポートは本プロダクトとは別プロジェクトとして作る
- seed は合わせて約 2000 語を想定し、ゆっくり消化する

## テレメトリ

生イベントを解釈せずに積む。

```
event(session_id, cycle_id, ts, type, payload)
  type: scroll_pos / word_tap / dict_lookup / rating /
        quiz_answer / cycle_start / cycle_end
```

wpm、スクロール逆行、ひっかかり箇所は `scroll_pos` の時系列から後で導出できるため、専用カラムは持たない。
クライアントでバッファし、サイクル終了時にまとめて送る。
当面は統計データに留めるが、将来「逆行が集中した段落の語は暗黙 `good` を取り消す」といった改良の材料になる。

## アーキテクチャ

ロジックはクライアントに寄せ、backend は DB と認証のみとする。

| レイヤ | 選定 | 補足 |
|---|---|---|
| フロント | React + Vite SPA + PWA | Workers Assets で静的配信。オフライン読解と OPFS 前提 |
| API | Hono on Cloudflare Workers | DB CRUD と OAuth のみの薄い API |
| DB | D1 | カード、レビューログ、生成済み文章のメタ、テレメトリ。ユーザーごとに行分離 |
| 認証 | Google OAuth | セッションは cookie |
| SRS | ts-fsrs(クライアント) | |
| 辞書 | SQLite WASM + OPFS | |
| LLM | クライアントから BYO API キーで直接呼び出し | キーはローカル保存し、サーバーに送らない |

BYO キーのため夜間 batch 生成はできないが、ストリーミングと先読み生成で待ち時間はほぼ消える。
コストは 1 日あたり出力 1 万 token 強であり、中位モデルで月数十円から数百円に収まる。

## 同期 API の transport 契約

- ブラウザの同期クライアントは `/api/sync` の GET/POST だけを扱い、認証 cookie は `credentials: "same-origin"` で同一オリジンの場合だけ送信する。クロスオリジン同期と CORS はサポートしない
- `baseUrl` は相対パス、または同一オリジンのテスト・デプロイ先を解決するための絶対 URL に限る。`//` で始まる protocol-relative URL は、期待するオリジンに解決できてもサポートしない
- Worker の POST は `Origin` ヘッダーを必須とし、`APP_URL` の origin と完全一致する場合だけ受け付ける。GET はブラウザ以外のクライアントのため `Origin` 省略を許可するが、提示された origin は同一でなければならない。クロスオリジン同期と CORS はサポートしない
- 成功した GET/POST の同期レスポンスは `Content-Type: application/json` を必須とし、`charset` などのパラメータは許可する。欠落または別の media type は generic な invalid-response として扱う
- 同期レスポンスと batch request は hard cap と bounded reader を持ち、cache は常に `private, no-store` とする。GET は超過検出のため各 top-level type を hard cap + 1 件までサーバー側で materialize してから generic な 413 を返す場合があるが、結果を切り捨てない。未対応メソッドも `/api/sync` 上では JSON の 405 を返す
